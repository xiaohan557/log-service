# 分布式日志收集与检索服务 —— 项目设计文档

> 版本：v1.0
> 技术栈：Java 17 + Spring Boot 3 + SQLite（WAL）+ Maven
> 交付物：HTTP 服务、CLI 工具、采集 Agent、单元测试、本文档

---

## 1. 项目概述

本系统实现一个分布式日志收集与检索服务，核心能力：

- 通过 **HTTP 协议** 提供日志的**上报、按条件查询、删除**三类接口。
- 日志**持久化**到 SQLite，并按**天**做时间分区存储（一张表存一天的数据）。
- 提供**采集 Agent**，支持**推送（push）**或**拉取（pull）**日志。
- 支持日志**级别**标记、**标签**、**过期自动清理**。
- 提供 **CLI 工具**：上报测试日志、查询日志、查看存储状态、启动采集 Agent。

### 1.1 名词解释

| 名词 | 含义 |
|------|------|
| 日志（Log） | 一条带时间、级别、标签、来源、正文的结构化记录 |
| 分区（Partition） | 按时间把日志拆到不同的物理表里，便于清理和查询 |
| 采集 Agent | 跑在业务机器上的客户端，负责把日志送到服务端（push）或从服务端拉回（pull） |
| 保留天数（Retention） | 日志最长保存多久，超期自动删除 |

## 2. 技术选型

| 项目 | 选择 | 理由 |
|------|------|------|
| 语言 | Java 17（LTS） | 考试要求 Java；17 是当前长期支持版本，生态成熟 |
| 构建 | Maven | Java 生态最普及的构建工具，依赖管理简单 |
| HTTP 框架 | Spring Boot 3.2 | 快速提供 REST 接口、JSON 序列化、定时任务，学习资料最多 |
| 存储 | SQLite（JDBC） | 嵌入式、零部署、单文件，满足持久化 + 分区 + 事务，适合教学和小型场景 |
| 单元测试 | JUnit 5 | Spring Boot 默认测试框架 |
| CLI/Agent 客户端 | JDK 内置 `HttpClient` + Jackson | 无需额外依赖即可调用服务端接口 |

> 为什么不用 PostgreSQL：考试允许 SQLite，且 SQLite 无需单独装数据库服务，对小白最友好，一条依赖即可运行。

## 3. 总体架构

```
                 ┌─────────────────────────────────────────────┐
  采集 Agent ───▶│              HTTP 服务（Spring Boot）         │
  （push 日志）    │                                             │
                 │   Controller 层（REST 接口 /api/logs 等）      │
  采集 Agent ◀───│        │                                     │
  （pull 日志）    │   Service 层（业务逻辑 + 定时清理）            │
                 │        │                                     │
  CLI 工具 ◀────▶│   Storage 层（SQLite 分区表读写）              │
  （上报/查询/     │        │                                     │
   状态/启动agent）│   SQLite 文件（logs_20261113 等按天分表）      │
                 └─────────────────────────────────────────────┘
```

- **分层**：Controller（接口）→ Service（业务）→ Storage（持久化），职责清晰、可测试。
- **分布式设计**：服务端是**无状态**的（状态全在 SQLite 文件里），可横向扩容：多个服务实例挂到负载均衡器后面，共享同一个存储（换成 PostgreSQL 即可无缝升级）。
- **Agent/CLI** 都是独立客户端，通过 HTTP 与服务端解耦。

## 4. API 接口定义

统一前缀：`/api`。所有时间参数均为 **Unix 毫秒时间戳**。返回统一结构（成功）：

```json
{ "code": 0, "msg": "ok", "data": ... }
```

### 4.1 日志上报

**单条上报**

```
POST /api/logs
Content-Type: application/json

请求体：
{
  "ts": 1760000000000,        // 可选，缺省用服务器当前时间
  "level": "ERROR",           // 必填：DEBUG/INFO/WARN/ERROR
  "tag": "order-service",     // 可选：日志标签
  "source": "host-1",         // 可选：来源主机/应用
  "message": "数据库连接超时"   // 必填：日志正文
}

响应 data：写入后的完整日志（含服务端生成的 id）
```

**批量上报**

```
POST /api/logs/batch
Content-Type: application/json

请求体：日志对象的 JSON 数组
响应 data：写入后的日志数组
```

### 4.2 条件查询

```
GET /api/logs?level=ERROR&tag=order-service&keyword=超时&startTs=1760000000000&endTs=1770000000000&limit=100&offset=0

参数（全部可选）：
  level    日志级别精确匹配
  tag      标签精确匹配
  keyword  正文模糊关键词（LIKE %kw%）
  startTs  起始时间戳（含）
  endTs    结束时间戳（含）
  limit    返回条数（默认 100）
  offset   偏移（默认 0）

响应 data：日志数组，按时间倒序
```

### 4.3 删除日志

**按 ID 删除**

```
DELETE /api/logs/{id}

响应 data：{ "deleted": 1 }
```

**按条件删除**

```
DELETE /api/logs?level=...&tag=...&startTs=...&endTs=...

响应 data：{ "deleted": 实际删除条数 }
```

### 4.4 存储状态

```
GET /api/storage/stats

响应 data：
{
  "dbPath": "data/logs.db",
  "dbSizeBytes": 204800,
  "partitions": [
    { "table": "logs_20261113", "rows": 1523 },
    { "table": "logs_20261112", "rows": 980 }
  ]
}
```

## 5. 存储设计（表结构 / 数据结构）

### 5.1 分区策略

- 按**天**分区：`logs_20261113`、`logs_20261112` …
- 分区键 = 日志产生时间 `ts` 对应的日期（本地时区）。
- 好处：过期清理 = 直接 `DROP` 整张旧表，快且简单；查询天然缩小扫描范围。

### 5.2 表结构（每张分区表结构完全一致）

```sql
CREATE TABLE IF NOT EXISTS logs_20261113 (
    id      TEXT PRIMARY KEY,   -- 全局唯一：<日期>-<8位随机hex>，例 20261113-3f2a9b1c
    ts      INTEGER NOT NULL,   -- 日志产生时间，Unix 毫秒
    level   TEXT NOT NULL,      -- DEBUG/INFO/WARN/ERROR
    tag     TEXT,               -- 标签，可空
    source  TEXT,               -- 来源，可空
    message TEXT NOT NULL       -- 正文
);
CREATE INDEX IF NOT EXISTS idx_logs_20261113_ts    ON logs_20261113(ts);
CREATE INDEX IF NOT EXISTS idx_logs_20261113_level ON logs_20261113(level);
CREATE INDEX IF NOT EXISTS idx_logs_20261113_tag   ON logs_20261113(tag);
```

> **为什么 id 是字符串而不是自增数字**：分表后每个表的自增 id 会重复，无法全局定位一条日志。把日期编码进 id（前 8 位），就能从 id 直接反推出它所在的表，实现 O(1) 的按 ID 删除。

### 5.3 内存中的数据结构

```java
class LogEntry {
    String id;      // 全局唯一 id
    long   ts;      // 时间戳
    String level;   // 级别
    String tag;     // 标签
    String source;  // 来源
    String message; // 正文
}

class QueryParams {
    String level; String tag; String keyword;
    Long startTs; Long endTs;
    int limit = 100; int offset = 0;
}
```

## 6. 日志写入流程

```
Agent/CLI 上报
      │ POST /api/logs
      ▼
LogController.report(entry)
      │
      ▼
LogService.report(entry)
      │ 1. 补全默认值（ts、level）
      │ 2. 根据 ts 计算日期 → 分区表名 logs_<date>
      │ 3. 若表不存在则先建表（CREATE TABLE IF NOT EXISTS + 建索引）
      │ 4. 生成全局唯一 id = <date>-<8位随机hex>
      │ 5. INSERT 到对应分区表
      ▼
LogStorage.insert(entry) → 返回带 id 的完整日志
```

批量上报走 `insertBatch`：按分区把日志分组，每组在一个事务里 `addBatch + executeBatch + commit`，保证一批要么全成功要么全失败。

## 7. 日志读取（查询）流程

```
GET /api/logs?level=...&tag=...&keyword=...&startTs=...&endTs=...
      ▼
1. 根据 startTs/endTs 确定涉及的分区表集合（若无时间条件则扫描全部分区表）
2. 对每张表拼 SQL：SELECT ... WHERE 1=1
   - level 精确匹配  → AND level = ?
   - tag   精确匹配  → AND tag = ?
   - 时间范围       → AND ts >= ? / AND ts <= ?
   - keyword 模糊   → AND message LIKE ?
3. 逐表查询，结果合并
4. 全局按 ts 倒序排序
5. 在内存中应用 limit / offset 后返回
```

> 说明：分页在内存中完成（先合并再截取），实现简单且对中小数据量足够；生产级可优化为 SQL 层分页。

## 8. 过期清理策略

- **策略**：按**分区表**清理。保留 `log.retention.days` 天（默认 30 天）。
- **触发**：Spring `@Scheduled` 定时任务，默认每 24 小时执行一次（间隔可配置）。
- **算法**：
  1. 从 `sqlite_master` 查出所有 `logs_%` 表；
  2. 解析表名中的日期；
  3. 若 `表日期 < 今天 - 保留天数`，执行 `DROP TABLE`；
  4. 记录本次删除的表数量。
- **优点**：`DROP TABLE` 是 O(1) 元数据操作，比逐行 `DELETE` 快几个数量级，且不产生碎片。

```java
cutoff = today - retentionDays
for table in allPartitionTables():
    if parseDate(table) < cutoff:
        DROP TABLE table
```

## 9. 异常崩溃恢复方案

| 风险 | 应对 |
|------|------|
| 进程崩溃时写入到一半 | SQLite 开启 **WAL 模式**（`PRAGMA journal_mode=WAL`），写入先落 WAL 再落主库；崩溃后下次启动自动重放/回滚，保证不损坏、不脏写 |
| 批量上报中途崩溃 | 批量写入包在**事务**里，`commit` 前崩溃则整批回滚，不会出现“半批成功” |
| 磁盘 I/O 崩溃 | `PRAGMA synchronous=NORMAL` 在性能与安全间取平衡；每次写入后 WAL 保证可恢复 |
| 启动时数据库损坏 | 启动流程执行 `PRAGMA integrity_check`，发现问题可重建；并自动 `CREATE TABLE IF NOT EXISTS` 补齐当天分区 |
| 服务重启后状态丢失 | 状态全在 SQLite 文件里，重启后自动恢复，服务端本身无内存态 |
| 并发写入冲突 | `PRAGMA busy_timeout=5000`，锁忙时等待而不是直接报错 |

**启动恢复流程**：

```
1. 打开 SQLite，设置 WAL / synchronous / busy_timeout
2. PRAGMA integrity_check 校验（可选）
3. 确保当天分区表存在（不存在则创建）
4. 启动定时清理任务
5. 服务开始对外提供接口
```

## 10. 并发与一致性

- SQLite 单写多读：WAL 模式允许**读不阻塞写、写不阻塞读**，多 Agent 并发上报时靠 `busy_timeout` 排队等待。
- 每条日志的 `id` 由服务端生成（日期 + 随机 hex），保证全局唯一、无竞态。
- 查询与清理可能并发：清理只 `DROP` 过期表，不会删除“今天”的表，因此与写入/查询天然不冲突。
